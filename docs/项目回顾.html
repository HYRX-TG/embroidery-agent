知绣坊项目回顾：功能全景 + 踩坑与解决方案

用途：隔了很久要重新捡起项目时，先读这一份。 项目路径：D:\embroidery_agent ｜ 规模：约 6300 行 Python、46 项测试、20 个 API 端点 状态：门店灰度可用（功能闭环完整），公网生产还差部署与账号体系

一、这个项目是什么

一句话：给刺绣门店做的本地离线 AI 客服 + 员工助手——客户咨询行业知识、自动收集定制需求成工单；员工查工艺、算运费、算报价、排产期、做质检、看经营数据。

为什么做：刺绣店有三个死结——① 老师傅经验在脑子里，新客服答不上；② 新人乱报价出过事；③ 报价、成本、客户资料绝对不能上传到在线大模型。所以全链路本地跑（Ollama + FAISS + SQLite），不调用任何外部 API。

核心设计哲学（贯穿整个项目）：

LLM 只做它擅长的"理解"和"表达"，所有确定性的事（算钱、权限、兜底）交给代码。

这条原则能解释项目里 80% 的设计决策，也是面试最能讲出深度的地方。

三、踩过的坑与解决方案（按主题分组）

这一节是整个项目最值钱的部分——每个坑都是真实跑出来的，都有代码证据。

A. 多轮对话与状态管理（踩坑最密集的区域）

A1. 用户问什么都被同一句客套话回答

现象：问"你们能做什么""刺绣难学吗""客服电话多少"，全都回同一句"您好呀~我是知绣坊的刺绣顾问…"

根因：意图分类器兜底返回 SMALL_TALK，而 customer.py 收到闲聊意图直接返回硬编码话术，根本不过模型。用户一句"这算什么自主回答"点破了这个问题。

解法：兜底一律改成 KNOWLEDGE 走 RAG + 模型；只有真正的短问候（"你好/谢谢/再见"）才用闲聊分支，且模型可用时也优先让模型回。

经验：兜底路径决定系统下限。兜底返回什么，用户就会大量遇到什么。任何"默认分支"都要按最常见的情况设计，不能当垃圾桶。

相关代码：nlp/intent.py 末尾、agent/customer.py 的 SMALL_TALK 分支

A2. 定制需求回答被当成知识问答吞掉

现象：收集需求时客户答"牡丹题材"、"手工绣"，系统却去检索知识库回答了，需求收集永远推不完。

根因：为了支持"收集中途客户顺带问知识问题"，我在 process 入口加了"跑题放行"判断——但用的是意图分类。而"牡丹题材""手工绣"都含工艺实体词，被分类成了 KNOWLEDGE，于是被误判为跑题。

解法（关键重构）：跑题判据改成——先做表单抽取，看本轮有没有新填字段。

  • 有新信息 → 客户在回答追问，继续收集
  • 无新信息 → 才可能是跑题提问，再走意图判断放行

经验：判断"用户这句话属于哪条流程"时，用流程自己的状态变化做判据，比用语义分类可靠得多。语义分类永远有边界模糊。

相关代码：agent/customer.py:_handle_requirement 的 new_info 判断

A3. 多轮收集时已填的字段莫名丢失

现象：客户答了尺寸，下一轮问工艺后，尺寸变成空了。

根因：每轮都把整段对话交给 LLM 做表单抽取，全量覆盖 session.requirement——模型抽漏或抖动，已确认的信息就被冲掉了。

解法：合并策略改为只填空字段，永不覆盖已有值。

经验：LLM 抽取类任务，默认策略应该是"增量合并"而不是"全量重写"。模型是有抖动的，不能让它的抖动破坏已确认状态。

相关代码：generation/answer.py:extract_requirement_form

A4. 表单字段全空，追问清单也找不到

现象：报 ValueError: '图案主题' is not in list

根因：missing_fields() 返回的是中文标签（"图案主题"），而 QUESTION_FLOW 的 key 用的是字段名（pattern_theme），两者对不上。

解法：QUESTION_FLOW 的 key 统一改成中文标签，并对不在清单里的字段加兜底提问。

经验：跨模块传值时，标识符类型要统一（要么全用英文 key，要么全用展示标签）。这类 bug 写的时候看不出来，跑起来才炸。

A5. 定制数量是必填项，但没有对应的追问话术

现象：其他都填完了，系统问"请问您还有别的信息想补充吗？比如定制数量~"——生硬，而且暴露了兜底逻辑。

解法：QUESTION_FLOW 补上数量追问，并让 missing_fields() 的顺序与追问顺序一致。

经验：必填字段清单和追问话术清单是两份数据，必须同源或加一致性测试，否则一定漂移。

A6. 整段流程"看起来"在跑，但字段一直是空的

现象：收集流程走了 7 轮，最后表单全空。

根因：Ollama 服务整个挂了（11434 拒绝连接），而 extract_requirement_form 在模型不可用时静默 return form——吞了异常，只留下"流程正常"的假象。

解法：① 抽取失败/跳过都写 WARNING 日志（form_extraction_skipped reason=llm_not_ready detail=...）；② 引入规则抽取器作为第一优先级，模型挂了也能收集。

经验：静默降级是运维炸弹。任何 except: pass 都要配一条日志。用户看到"流程在走"，开发者看到"全是空的"，中间只差一条日志。

B. 模型与推理接入

B1. 模型被删了，服务显示"就绪"，回答全是降级

现象：/api/v1/status 显示 llm_ready: true，但所有回答都是"知识库直接引用"的粗糙风格。

根因：is_ready() 只 ping /v1/models 看 HTTP 200，不检查目标模型在不在模型列表里。qwen2.5 被删后，服务照样返回 200。

解法：is_ready() 同时校验模型名是否存在；新增 missing_reason() 输出"模型 X 未安装，可用模型：[...]"；每次降级写日志。

经验：健康检查要检查业务可用的那件事，不是"进程活着"。模型服务 ping 通 ≠ 能推理。

相关代码：generation/llm.py:is_ready / missing_reason

B2. 换模型要改代码吗？不用

设计：所有业务代码只面向 OpenAI 兼容接口（/v1/chat/completions）编程，模型名在 configs/default.json 一行配置。

实战验证：qwen2.5:7b 被删后，改一行 chat_model 切到 qwen3.5:9b，重启即生效，业务零改动。

代价（要如实知道）：9B（6.6GB）在 8G 显存里装不满，部分层跑 CPU，热启动后约 4 字/秒——一段 200 字回答要 40-50 秒。7B Q4（4.7GB）能全进显存，速度快约一倍。这是显存换质量的物理权衡，不是配置问题。

经验：应用层与推理层解耦的收益在"换模型时"结算。提前花的成本很小（只调 API），收益很大。

B3. 构建知识库时模型没启动，直接报错崩掉

现象：build_kb.py 抛 httpx.ConnectError

解法：embedding 失败 → 降级为仅 BM25，输出 vector_ok: false + warning，不阻断构建。

经验：数据构建类脚本要"能降级跑完"，否则换台机器就卡在第一步。

B4. reranker 一加载就卡死十分钟

现象：请求 /api/v1/status 卡住不动。

根因：首次加载 bge-reranker-base 触发 HuggingFace 在线下载，国内网络超时 + 自动重试 5 次。

解法：离线优先——本地 HF 缓存里没有该模型就直接跳过精排，绝不触发网络请求；需要时提前手动下载。

经验：离线系统里任何隐式网络请求都是定时炸弹。第三方库的"自动下载模型"行为要在初始化前拦住。

B5. 花力气做的 reranker，实测反而让效果变差

做法：下载 bge-reranker 做两阶段检索（召回 20 → 精排 5）。

A/B 结果：黄金集 Top1 命中 91.1% → 84.8%（Top5 仍 100%）。

决策：默认关闭，配置里保留开关并写明实测数据。

经验：小规模中文行业库里，精排模型的噪声可能大于信息增益。功能加完要用数据验收，负收益就敢关掉——这比"功能越加越多"更能说明工程素养。

相关代码：configs/default.json:rerank.enabled=false 及注释

C. 检索与知识库

C1. 改了知识库，检索还是旧内容

根因：索引是离线构建的产物，文件改了不重建就不生效。

解法：manifest 机制——记录每个源文件的 mtime + size 和 embedding 模型名，每次加载时比对，不一致自动重建。

经验：缓存要有失效机制。手工维护的"记得重建索引"最终一定会忘。

相关代码：retrieval/pipeline.py:_kb_stale / _manifest

C2. 中文 session_id 直接 500

现象：传中文 session_id 时请求 500，日志是 UnicodeEncodeError: 'latin-1' codec can't encode。

根因：HTTP 响应头只能 latin-1。我把 session_id 放进了 X-Session-Id 响应头。

解法：服务端检测非 ASCII 就换成新生成的 ID。

经验：HTTP header 不是兜里，只放 ASCII。用户可控的值要过滤后再进 header。

C3. 评测脚本读 JSONL 报 "Extra data"

根因：黄金集是 JSONL（每行一个对象），脚本用 json.loads 读整个文件。

解法：按行解析。

附带问题：多轮对话数据集是跨行 JSON（不是严格 JSONL），逐行解析必炸。解法是按大括号配对切块解析。

经验：JSONL 和"多个 JSON 拼在一起"是两种格式，解析器要能区分。

D. 安全与权限

D1. 客户能看到系统内部信息

现象：前端右侧栏暴露了模型名、知识库块数、工单列表——客户也看得到。

解法（双层）：

  • 前端：客户视图根本不渲染侧栏（视图隔离）
  • 后端：/status、/tickets、/staff/chat、/search?role=staff、工具直调等内部端点全部要求员工口令（防绕过前端直接调 API）

经验：前端隐藏 ≠ 权限控制。所有权限必须有服务端校验，前端只是体验。

D2. 员工口令明文存在配置文件里

解法：三档（明文 → SHA-256 哈希 → 环境变量），发布 GitHub 前把明文清空只留哈希。

经验：发布开源仓库前跑一遍 git diff | grep 查密钥，这是固定动作。

D3. 一个脚本就能打满 7B 模型

解法：进程内滑动窗口限流（按 IP + 桶）。

局限（要诚实）：单进程版，多实例部署需换 Redis 之类的共享存储。

D4. 客户可能诱导模型泄露内部信息

解法：双层——规则层 guard.py 拦截 9 类模式（忽略指令/越狱/套系统提示/套底价），命中即礼貌拒绝 + 审计日志；prompt 层写"安全防线最高优先级"条款。

经验：prompt 是软约束，不能当唯一防线。能用代码判定的，就不要交给 prompt。

E. 前端交互

E1. 回车键不能发送

根因：<textarea> 的回车默认是换行，不触发表单提交。

解法：监听 keydown，Enter 且非 Shift 时 preventDefault + 发送；Shift+Enter 保留换行。

E2. 打开页面 404

根因：server.py 里漏了静态文件挂载。

解法：补 StaticFiles 挂载 + 根路由返回 index.html。

F. 数据与外包决策

F1. 想找刺绣开源数据集，反复确认：不存在

搜索结论：GitHub 上刺绣相关仓库全是制图软件（inkstitch、pyembroidery、Embroidermodder），没有任何知识文本数据集；维基百科/百度百科在当前网络下超时或 403。

最终方案：NCIFD 民族文化开源数据集（698 条工艺问答，关键词过滤）+ 本仓库原创整理的纹样民俗百科、行业经营常识，每份都在 SOURCES.md 声明来源和许可。

经验：垂直行业往往没有现成数据。"没有数据"本身是竞争壁垒——你整理的私有知识库就是资产。同时要养成数据溯源习惯。

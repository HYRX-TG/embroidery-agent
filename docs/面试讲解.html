知绣坊项目面试讲解手册（Agent 开发工程师方向）

目标：让你能像"自己从零做过"一样讲这个项目。分四部分：① 三档项目介绍（背）；② 模块深讲（为什么这样设计）；③ Agent 岗高频追问预演；④ 量化数字卡片。

一、三档项目介绍（直接背）

30 秒版（开场）

我做了一个刺绣行业的私有化本地离线智能客服 Agent。背景是刺绣这种传统行业，客户咨询、报价、定制沟通高度依赖老师傅经验，而业务数据（报价、成本、客户）不能出内网。所以整个系统全离线：Qwen 本地模型推理 + bge-m3 向量检索 + FAISS，FastAPI 做服务层。核心是双角色设计——C 端客户只能查公开行业知识，问价格一律转人工；B 端员工有内部知识库和 6 个专家 Agent（报价/排产/物流/质检/经营）。我在架构上做了一个关键决策：所有业务数值由确定性纯函数核算，LLM 只负责理解需求和解释结果，杜绝了大模型算错价格的生产事故。项目有 46 个单元测试、146 条黄金评测集，检索 Hit@1 79%、行为合规率 98%。

3 分钟版（展开讲，加上下面这些点）

在 30 秒版基础上补三层：

  1. 为什么做 Agent 而不是套壳 Chatbot：客服场景有"多轮状态"（定制需求要追问 6 个字段）、"业务动作"（建工单、算报价）、"权限边界"（内部知识不能给客户看）——这三件事纯 prompt 都做不干净，所以我做了意图路由 + 会话状态机 + 工具调用三层。
  2. 多 Agent 团队怎么协作：一个 TeamOrchestrator，路由分两级——强业务信号（"报价/运费/交期"）用正则直接命中专家，零延迟零成本；知识问句才走 LLM JSON 路由（带 LRU 缓存）。每个专家是"三段式"：LLM 提参数 → 纯函数算结果 → LLM 流式解释。
  3. 质量怎么保证：我吃了亏才建的评测闭环——146 条黄金测试集每条标注"期望来源 + 期望意图 + 期望行为"三个维度，改任何提示词/规则/知识库都跑回归；上线后真实对话通过数据飞轮脚本导出成微调候选。

10 分钟版（深挖时讲）

再加上：外挂知识库协议设计（见下文第四部分）、安全攻防（注入防御/权限三层隔离）、踩坑故事（见第二部分末尾）、生产化路线（灰度 → 补工单闭环 → 公网）。

二、模块深讲（每块都答"为什么"）

1. 整体架构（自底向上）

前端（客户页 + 团队工作台，原生 JS + SSE）
  ↓
FastAPI（统一鉴权 / IP 限流 / SSE 流式 / 渠道 webhook）
  ↓
Agent 层
  ├─ CustomerAgent：意图分类 → 需求追问状态机 → 工单
  ├─ TeamOrchestrator：路由 → 6 个专家 Agent
  │     └─ 专家 = LLM 提参（JSON mode）→ business_tools 纯函数 → LLM 解释
  └─ StaffAgent：内部知识 + 复盘 + 文案
  ↓
检索层：BM25(jieba) + FAISS(bge-m3) → RRF 融合 → 角色权限过滤 → 可选 rerank
  ↓
数据层：data/knowledge(公开) + data/internal(仅员工) + data/team_kb(团队外挂) + SQLite(会话/工单)
模型层：Ollama（OpenAI 兼容接口，换模型改一行配置）

为什么 Ollama 而不是 vLLM/llama.cpp：单机 Windows、并发低，Ollama 原生支持 Windows 且暴露 OpenAI 兼容接口；我的业务代码只面向 /v1/chat/completions 编程，换 vLLM 不用改一行——这是"应用层与推理层解耦"，换模型（7B→9B→微调版）只改 chat_model 一行配置。我实际经历过两次换模型验证这一点。

2. 双角色权限（三层隔离）——必考题

  • 数据层（最硬）：每个知识 chunk 带 visibility: public/internal，检索器在召回前按角色过滤候选集——客户根本检索不到内部库，而不是"检出来再靠 prompt 别说"。prompt 是软约束，数据过滤是硬边界。
  • Prompt 层：C 端 / B 端两套 system prompt，风格与能力边界完全不同。
  • 能力层：报价/排产/经营查询工具只注册给 B 端专家；C 端只有"咨询 + 登记意向单"。
  • 端点层：所有返回内部信息的 API（status/tickets/staff chat/staff search/tools）统一过 require_staff，用 hmac.compare_digest 做常量时间比较防时序侧信道。

3. 意图路由与需求追问状态机

  • 意图分类是规则先行：关键词 + 工艺实体词典（针法/品类/纹样/材料）命中，零延迟零成本、完全可解释；LLM 路由只在团队侧做兜底。
  • 客户表达"定制意向"后进入 collecting 状态机：按固定顺序（主题→尺寸→工艺→用途→预算→交付）每轮只追问 1 个；客户说的碎片信息由 LLM 以 JSON mode 结构化抽取进 RequirementForm，合并策略是只填空字段不覆盖（早期版本每轮全量重写，丢字段，修掉了）。
  • 两个边界我专门处理过：① 收集中途客户问知识题 → 先放行回答、保持收集状态（跑题放行）；② 客户说"不用了/算了" → 退出收集。
  • 兜底设计是红线：分类器没命中任何规则时必须走"知识咨询"交给模型，绝不能退化成固定话术——我早期犯过这个错（兜底返回 SMALL_TALK 硬编码回复），用户一句"这算什么自主回答"点醒我，修完所有未命中问题都由 RAG + 模型真实回答。

4. 确定性工具 vs Function Calling（Agent 岗最核心的考点）

我的观点（面试就这么讲）：LLM 直接算数不可靠，尤其是乘加混合的运费/报价——所以我把"算"从"说"里剥离：

  • business_tools.py 全是纯函数：运费（重量+体积重抛比+分区）、报价（面积×工艺单价×数量+装裱）、排产（工序串并行+产能）；价格表和产能参数在 configs/*.json，业务运营自己能改，不用动代码。
  • LLM 只做两件事：参数提取（JSON mode，先正则快路径——"60乘80/手工绣/3幅"直接命中，不调模型；缺参才调 LLM 且带对话历史，支持省略句"那只要 5 幅呢"从上文继承）和结果解释（把计算结果翻译成客户话术）。
  • 效果：模型"说出来的价格"和系统"算出来的价格"天然一致，幻觉在数值层面被结构性消灭——这比任何 prompt 约束都可靠。

5. 检索管线

  • 双路召回：BM25（jieba 分词，抓专有名词精确匹配）+ FAISS（bge-m3 1024 维，内积+L2 归一化=余弦），RRF 融合排序。
  • 为什么两路：BM25 对"打籽绣/盘金绣"这类术语精确命中强，向量对"绣品发霉怎么办→保养"这类语义改写强，单路都有明显盲区（评测数据支撑）。
  • rerank 的教训：我下载了 bge-reranker-base 做两阶段检索，A/B 实测发现黄金集上 Top1 命中从 91% 降到 85%（Top5 不变）——重排模型对小规模中文行业库反而引入噪声，所以默认关闭、保留开关。这个"实测后关掉自己加的功能"的故事比功能本身更能体现工程素养。
  • 索引自愈：manifest 记录每个源文件 mtime+size+embedding 模型名，请求进来先比对，变更自动重建——避免"改了知识库忘建索引"的经典事故。
  • 降级链：Ollama 挂→BM25 单路；LLM 挂→抽取式回答（直接引用知识库原文+来源）；全挂→固定兜底话术。每级降级写 WARNING 日志（llm_fallback reason=...），状态页的 llm_ready 会真检测模型是否安装（曾发生模型被删、服务"假在线"的事故，修的）。

6. 会话与记忆

  • 会话（消息、需求表单、collecting 状态）落 SQLite（WAL 模式），重启不丢；前端 localStorage 存 session_id，跨刷新续聊。
  • 多轮上下文窗口只取最近 8 条消息进 prompt——控制 token 也控制跑题；团队侧参数提取带历史解决指代省略。
  • 意向分级（高/中/低）是确定性规则（六要素齐全=高意向可报价），工单自动打标，帮销售排优先级——又是"规则能做的不用模型"。

7. 安全（离线系统也要攻防）

  • 提示词注入：正则模式库拦截"忽略指令/越狱/扮演/套取系统提示/套取底价"，命中即礼貌拒绝并记审计日志；同时 system prompt 写"安全防线最高优先级"条款——软硬两层。
  • 口令：明文（开发）→ SHA-256 哈希（配置不落明文）→ 环境变量注入（生产），三档。
  • 限流：按 IP 滑动窗口（对话 10/分、检索 30/分），防止一个脚本打满 7B 模型。
  • XSS：工单列表前端用 DOM textContent 渲染而非 innerHTML。
  • 发 GitHub 前清了明文口令（配置只留哈希，演示口令写进 README 提醒替换）。

三、外挂知识库怎么讲（用户点名要的重点）

一句话定位：agent/rag.py 定义了 RAGProvider 协议（retrieve(query, top_k) -> list[chunk]），团队所有专家通过统一入口 team_rag 取知识——知识从哪来，和 Agent 怎么用知识，完全解耦。

分层设计（讲清这三层就赢了大部分候选人）：

  1. 协议层：RAGProvider 是个 5 行的抽象接口。当前实现是 VectorRAGProvider（bge-m3 + FAISS）；接企业私有库（ES、Milvus、甚至网盘文档解析器）时只需新增一个类实现这个协议，改一行 team.rag_provider 配置指向它，所有专家立即切换——业务代码零改动。
  2. 数据层：data/team_kb/ 是外挂挂载点，已有两个来源：NCIFD 民族文化开源数据集（GitHub，698 条工艺问答，关键词过滤离线使用）+ 本仓库整理的纹样民俗/经营常识。每个来源在 SOURCES.md 里声明出处和许可——知识资产的可溯源和代码一样重要。
  3. 运维层：独立索引目录 data/index/team_rag，源文件变更自动重建；RAG 状态有专门端点 /api/v1/team/status 可观测；回答强制带 [编号] 来源引用，客户可核对、质检可追溯。

面试官可能追问：

  • "为什么不直接用 Dify/RAGFlow？"——它们是平台，解决的是"快速搭"；我的场景要的是"深度定制权限、话术和确定性工具"，且要离线单机部署。但知识库边界上我借鉴了它们"数据源可插拔"的思想，抽象成了协议。
  • "怎么保证外挂数据质量？"——入库三关：来源声明（SOURCES.md）+ 关键词/主题过滤 + 黄金评测集回归（改知识库跑 evaluate，Hit@K 掉了就查）。
  • "客户数据怎么进这个库？"——数据飞轮：export_conversations.py 从真实会话导出问答对、自动过滤固定话术、人工审核后入库——知识库随业务运营持续生长，这是"外挂"而不是"一次性导入"的原因。

四、踩坑故事（面试加分项，讲细节才像真做过）

  1. .format() 撞 JSON 花括号：需求表单 prompt 里含 JSON 模板，用 .format(conversation=...) 注入对话时 {pattern_theme} 被当成占位符，抛 KeyError。改成 .replace("{conversation}", ...)。教训：模板里有字面花括号时别用 format。
  2. 中文 session_id 打爆响应头：HTTP header 只支持 latin-1，客户会话 ID 含中文时 UnicodeEncodeError 500。服务端对非 ASCII session_id 自动换新 ID。
  3. 意图兜底吞问题："你们能做什么"没命中关键词→被判闲聊→返回硬编码客套话，根本不过模型。修：兜底一律走知识咨询；只有真正的问候语才用固定话术，且模型可用时也优先让模型答。
  4. 模型被删、服务"假在线"：is_ready() 只 ping 服务端点，/v1/models 返回 200 就算就绪——模型被删后所有对话静默降级成引用式回答，没人发现。修：is_ready 同时校验目标模型在模型列表里；降级时 WARNING 日志带诊断原因。
  5. rerank 负收益：加了 reranker 反而降准确率（见上），敢关掉自己加的功能。
  6. 多轮表单丢失字段：每轮 LLM 全量重写表单→已收集字段被吞。修：合并策略只填空字段。

六、高频追问预演（快问快答）

Q: RAG 和微调怎么选？你为什么 RAG 为主？

知识更新频率决定：绣品种类、价格、话术会频繁变，微调改一次知识要重训；RAG 改文档重建索引秒级生效且可溯源。微调适合"改风格和能力"（话术调性、表单提取格式），我用数据飞轮攒真实对话，量到 1000+ 条再 QLoRA 微调 Qwen——两者是互补不是二选一。

Q: 你的 Agent 和 LangChain/LangGraph 有什么区别？为什么不用？

我手写了路由、状态机、工具调用三件事，总量可控（单文件几百行），换来的是完全可调试可解释。LangChain 的抽象层在排查 prompt 与检索问题时反而隔了一层。但我保留接口习惯（RAGProvider 协议、OpenAI 兼容接入），要迁到 LangGraph 编排时成本也低。小体量自研 > 引入重框架，是我的判断。

Q: 怎么评估你的 Agent 好不好？

三层：检索单测（Hit@K/MRR，黄金集）、意图单测（准确率）、行为合规（转人工率、该报价没报价）——最后一层最贴业务：一个"聪明但乱报价"的客服在生产上是负资产。

Q: 最大的技术挑战？

不是模型，是"确定性"：让 LLM 系统在业务红线（报价/权限）上像传统软件一样可靠。解法是把 LLM 关在笼子里——数值计算出笼、权限过滤在检索层、兜底话术在代码层。

Q: 多 Agent 会不会过度设计？两个 Agent 不够吗？

C 端一个 Agent 确实够；B 端专家拆开是因为职责和权限不同（报价专家能读成本参数，客服不能），拆分让每个专家的 prompt、工具、可访问配置天然隔离——多 Agent 在这里是权限边界的载体，不是炫技。

面试前一晚：把"30 秒版"背到脱口而出，把 6 个踩坑故事各讲一遍（每段 30 秒），外挂知识库三层设计画一遍。

# 第零部分：业务落地视角——怎么把老板的一句话变成跑起来的系统（应用工程师主叙事）

## 0.1 客户的原话 vs 真实需求（需求澄清是第一生产力）

客户的初始诉求往往是一句话：**"我想给我们刺绣店弄个 AI 客服。"**

直接照做就掉坑里了——"AI 客服"只是载体。应用工程师的第一步是**蹲到门店去搞清楚：客服每天在干什么、哪里赔钱、哪里耗人**。我做需求澄清后把"做个 AI 客服"翻译成了五条可验收的业务目标：

| 老板的模糊想法 | 澄清后的真实诉求 | 验收标准（和老板对齐的） |
|---|---|---|
| "客户问的问题新客服答不上" | 行业知识要沉淀成标准答案 | 新客服借助系统一次答对常见问题，回答带出处 |
| "新人乱报价出过事" | **报价必须可控** | 系统永远不报价，价格 100% 人工核算，需求参数自动收集 |
| "客户描述半天需求，记录还是乱的" | 需求收集标准化 | 每个定制咨询结束产出结构化表单+工单 |
| "报价单和别家对不上，口径乱" | 计算口径统一 | 同样的参数任何人/任何时候算出同一个价 |
| "我们的价格成本绝对不能上云" | 数据不出内网 | 全链路离线，审计无外网调用 |

**面试话术**："客户说要做 AI 客服，我做的第一件事不是选模型，而是在门店蹲了两天记录客服的每类对话——最后发现 80% 的问题集中在四类，而且**真正的痛点是报价失控和数据安全，不是'聊天'本身**。需求的澄清质量决定了后面所有技术选型。"

## 0.2 方案对客沟通：怎么让非技术老板听懂并签字

给老板的方案从来不是"架构图"，是**三笔账 + 一个边界**：

**第一笔：数据安全账**。在线 API 方案 = 客户资料/报价成本过第三方，泄露风险与合规问题；本地离线方案 = 一次投入硬件（现有 8G 显存电脑即可），数据物理不出店。→ 老板秒懂，这是签字的关键。

**第二笔：成本账**。对比表：SaaS 客服（月费+数据在他那）/ 云端 API 自建（按 token 月付+数据在他那）/ 本地自研（一次部署+电费，数据在自己这）。三方案同一张表，老板自己就会选第三列。

**第三笔：人力账**。系统接住的是"重复咨询+需求记录"，省的是客服培训和响应时间；报价/成交仍由人做——**预期管理**：不承诺"替代客服"，承诺"新员工上手周期从两周到两天、客服响应零延迟、报价零事故"。

**一个边界（合同里写清楚的）**：AI 不做最终决策——报价、工期承诺、售后裁定永远人工。这不是技术妥协，是**业务风险设计**：让系统承担"确定性部分"，人承担"担责部分"。

## 0.3 落地节奏：三阶段交付（每阶段都要有客户可感知的产出）

| 阶段 | 周期 | 交付物 | 验收方式（客户视角） |
|---|---|---|---|
| **MVP 验证** | 1-2 周 | 知识问答 + 不报价兜底 + 需求表单，店内电脑跑通 | 老板拿 20 个真实客户问题现场试，答不上的记进"知识缺口清单"（本身就是交付物） |
| **门店灰度** | 2-4 周 | + 员工工作台 + 工单 + 意向分级；客服日常真实使用 | 看三个数：重复问题人工介入率下降、需求表单完整率、有没有出报价事故 |
| **生产放量** | 1-2 月 | + 微信公众号接入 + 服务自启/备份 + 数据飞轮 | 粉丝消息全自动应答、断电重启自恢复、每周知识库更新一次 |

**为什么这个顺序**：先在高风险低价值的问答域证明可靠性（出错了老板没损失），再碰工单这种业务数据，最后才对外接客——**每一步的失败成本都被前一步兜住**。

## 0.4 生产角度的关键设计（不是代码，是运营决策）

1. **人工兜底是产品功能，不是降级**：转人工不是"AI 不会了"，而是设计出来的分流——系统把 80% 重复劳动接走，20% 高价值决策（报价/成交/客诉）留给人，还自动把上下文整理成工单递过去。
2. **知识库的运营归属**：交付时培训店员"发现 AI 答错→改 md 文件→自动生效"，让**业务人员成为系统运营者**——应用工程师交付的是"会生长的系统"，不是一次性项目。
3. **数据飞轮 = 第二期收入**：真实对话自动导出成微调候选，攒够 1000 条做 QLoRA——给老板的路线图里写明"系统会越用越懂你的店"，这是续费/二期故事的锚点。
4. **成本底线**：全程本地=运行成本≈电费；8G 显存消费级电脑就能跑——小商户的 IT 预算现实。
5. **度量看板**（给老板的周报）：意向工单数、高意向占比、知识缺口条数、人工介入率——全是系统自动出的数。

## 0.5 风险清单与应对（主动讲出来才显成熟）

| 风险 | 应对 |
|---|---|
| 模型幻觉报错价 | 数值计算结构性剥离（纯函数），红线词硬拦截 |
| 断电/重启丢会话 | SQLite(WAL) 持久化 + NSSM 自启 + 每日备份 |
| 客户问倒知识库 | 兜底转人工 + 缺口自动记录 → 运营闭环 |
| 增长后单机瓶颈 | 路线图预留：多实例 + 共享限流 + 换 vLLM（接口已解耦，迁移成本低） |
| 老板预期漂移 | 三阶段验收标准签约时对齐，每阶段用"客户视角验收"复盘 |

# 第一部分：设计思路——先有问题，再有方案

## 1.1 业务起点：刺绣门店的五个真实痛点

面试官问"你解决什么问题"，从这里讲起——**每一个技术模块都对应一个具体痛点**：

| # | 门店痛点 | 直接后果 | 系统必须做到 |
|---|---|---|---|
| 1 | 老师傅经验在脑子里，客户问"打籽绣和盘金绣区别""牡丹什么寓意"，新客服答不上 | 客户觉得不专业，丢单 | 把行业知识做成**可检索的知识库**，回答带出处 |
| 2 | 客户一问价格，新人就慌：报高了吓跑人，报低了亏本，报错了没法收场 | 报价事故=真金白银损失 | **系统永远不报价**：价格类问题固定话术转人工，只收集需求参数 |
| 3 | 定制需求沟通靠聊，聊完信息散在微信记录里，店长接手要重新问一遍 | 客户重复描述，体验差，丢单 | **结构化需求收集**：按固定顺序追问，产出标准表单+工单 |
| 4 | 报价/运费/交期依赖老师傅心算，口径不统一 | 同一单不同人算出不同价 | **确定性计算器**：价格表配置化，谁算结果都一样 |
| 5 | 报价、成本、客户资料是商业机密，绝不能上传到任何在线大模型 | 数据外泄风险不可接受 | **全程本地离线**：模型、检索、数据、日志都不出内网 |

## 1.2 五个痛点 → 五组技术需求 → 选型推导

**痛点 1（知识沉淀）→ 需要"检索增强生成"**
- 候选：全靠微调（知识更新要重训，改一篇文档救不了）/ 纯 prompt 塞知识（上下文装不下 60+ 篇文档）/ **RAG**（改文档即生效、可溯源）✅
- 追加选择：中文行业词多（打籽绣/盘金绣），纯向量检索对精确术语不如关键词 → **BM25 + 向量双路召回 + RRF 融合**；权限要求（内部库对客户不可见）→ **召回前过滤**而不是召回后靠 prompt 约束。

**痛点 2（不报价红线）→ 需要"意图识别 + 兜底路由"**
- 不能指望 LLM 自己"记住别报价"（prompt 是软约束）→ 三道防线：**关键词拦截**（价格/工期/库存词命中→根本不进模型，直接返回转人工话术+建工单）→ **检索层权限过滤**（客户召回不到含价格的内部文档）→ **system prompt 红线**（最后一层软约束）。

**痛点 3（需求收集）→ 需要"对话状态机 + 结构化抽取"**
- 纯 prompt 让模型"自己多轮收集"不可控（可能一次问三个问题、可能漏字段）→ **显式状态机**：`collecting` 标志 + 固定追问顺序（主题→尺寸→工艺→用途→预算→交付）+ 每轮只问一个；客户回答用 **LLM JSON mode 抽取**进 `RequirementForm` 数据类，**合并策略只填空字段不覆盖**（防止后一轮抽取把已确认的字段冲掉）。

**痛点 4（计算口径）→ 需要"确定性工具 + LLM 解耦"**
- 这是整个项目最核心的架构决策：**LLM 是概率模型，不能让它算钱**。
- 方案：`business_tools.py` 纯函数（运费/报价/排产）+ 价格表外置 `configs/logistics.json`、`production.json`；LLM 只做两件事——**提参数**（JSON mode，且先走正则快路径："60乘80/手工绣/3幅"这种直接命中，零模型调用）和**解释结果**（把计算输出翻译成话术）。
- 效果：模型说出的价格=系统算出的价格，**数值幻觉被结构性消灭**。

**痛点 5（离线）→ 需要"本地模型栈"**
- 推理：**Ollama**（Windows 原生、OpenAI 兼容接口）；Embedding：**bge-m3**（Ollama 端）；向量库：**FAISS**（嵌入式，不用起 Milvus 服务）；数据库：**SQLite**（WAL 模式）。
- 关键架构约束：**业务代码只面向 OpenAI 兼容接口编程**——换模型/换推理引擎（7B→9B→微调版→vLLM）改一行配置，业务零改动。这是"应用层与推理层解耦"。

## 1.3 硬约束如何收窄选型

- **8G 显存**：7B/9B Q4 量化（4.7~6.6GB），embedding 放 CPU；纯 CPU 降级 3B。
- **零 API 费用**：不接任何云端 LLM——也顺带满足了痛点 5。
- **单机单进程**：限流用进程内滑动窗口（多实例才需要 Redis）；会话/工单 SQLite 够用。
- **Windows 门店电脑**：start.ps1 一键启动、NSSM 注册服务、PowerShell 运维脚本。

## 1.4 诉求 → 模块映射总表（背这张表）

| 诉求 | 对应模块 |
|---|---|
| 知识沉淀+可溯源 | `data/knowledge` + `retrieval/` + `generation/answer.py`（回答带[编号]来源） |
| 不报价红线 | `nlp/guard.py` + `customer.py:PRICE_SPECIAL_TERMS` + 权限过滤 + prompts 红线 |
| 需求收集 | `core/schema.py:RequirementForm` + `customer.py` 状态机 + `answer.py:extract_requirement_form` |
| 计算口径统一 | `agent/business_tools.py` + `configs/logistics.json` / `production.json` |
| 全程离线 | Ollama + bge-m3 + FAISS + SQLite + `generation/llm.py`（唯一出网口=本机 11434） |
| 员工生产力 | `agent/team.py + experts.py`（6 专家）+ `prompts/team/` 热更新 |

# 第二部分：一条消息的一生（把所有文件串起来）

## 链路 A：客户问"我想定制一幅绣品送长辈"

1. **前端** `web/app.js`：Enter 键发送 → `fetch POST /api/v1/customer/chat`（带 localStorage 里的 session_id）。
2. **API** `api/server.py:customer_chat`：IP 限流检查（`api/rate_limit.py` 滑动窗口）→ session_id 归一化（非 ASCII 自动换新，防 HTTP header 编码炸）→ 交给 `CustomerAgent`。
3. **Agent** `agent/customer.py:process`：
   - 注入检测（`nlp/guard.py`）：命中"忽略指令/套底价"→ 礼貌拒绝，流程终止；
   - 价格词拦截（`PRICE_SPECIAL_TERMS`）：本例没有；
   - 意图分类（`nlp/intent.py`）：命中"定制/送"触发词 → `CUSTOM_REQUIREMENT`；
   - 进入收集模式 `collecting=True`：本轮缺"图案主题" → 按追问顺序取第一问，SSE 流式返回。
4. **客户继续答**"牡丹题材"：classification → `collecting` 分支 → `generation/answer.py:extract_requirement_form` 用 LLM JSON mode 从对话抽字段，合并进表单 → 仍缺字段 → 问下一个 → …… 六要素齐 → 输出【表单+方案建议+待人工确认】，`agent/ticket.py` 写 SQLite 工单，`agent/leads.py` 规则打意向分（六要素齐=高）。
5. **知识类问题**（"苏绣和湘绣的区别"）走另一分支：`retrieval/pipeline.py:HybridRetriever.search` → 角色过滤（客户只见 public）→ BM25（`retrieval/bm25.py`，jieba 分词）+ FAISS（`retrieval/vector.py`，bge-m3）双路 → RRF 融合 → 可选 rerank → `generation/answer.py:customer_messages` 拼带编号来源的上下文 → `llm.py` 流式调 Ollama → 边生成边 SSE 推给前端逐字显示 → 全文落 SQLite 会话表。

## 链路 B：员工在团队工作台问"60×80 手工绣挂画 3 幅报价多少"

1. `web/team.html` → `POST /api/v1/team/chat`（带 `X-Staff-Access` 口令头）→ `server.py` 过 `require_staff`（hmac 常量时间比较）。
2. `agent/team.py:TeamOrchestrator.route`：**关键词正则先走**——"报价"命中 `quotation` 专家，零延迟；只有知识问句才走 LLM JSON 路由（带 LRU 缓存）。
3. `agent/experts.py:ToolExpert` 三段式：
   - **提参**：正则快路径直接命中"60×80/手工绣/3"→ 不调模型；缺参才 LLM JSON 提取（带历史，支持"那只要 5 幅呢"省略句）；仍缺 → 返回中文补参提示，不瞎猜；
   - **核算**：`agent/business_tools.py:order_quote` 纯函数按 `configs/production.json` 价格表计算；
   - **解释**：`experts.py:build_messages` 把工具结果注入 messages → LLM 流式解释（团队 RAG 的 `team_rag.py` 还会检索 `data/team_kb` 注入行业知识）。
4. 专家提示词来自 `prompts/team/quotation.md`（`prompt_store.py` mtime 热加载，改完即生效不重启）。

## 链路 C：微信公众号客户发消息

1. 平台回调 `GET/POST /api/v1/channels/wechat/webhook` → `channels/hub.py:ChannelHub.handle_webhook`。
2. `channels/wechat.py:WeChatAdapter`：GET 验签（token+sha1）回 echostr；POST 解析 XML 为 `IncomingMessage`。
3. `channels/base.py:ChannelStore`：openid → `get_or_create_session`（同一粉丝永远同一会话，跨设备不丢上下文）；消息 ID 幂等去重（微信会重推）。
4. 复用链路 A 的 `CustomerAgent` 生成回答 → 微信 5 秒被动回复限制 → **异步**：先回空串，答案进 `channel_pending_replies` 队列，凭 app_id/secret 调客服消息接口推送；未配凭证=本地模式（回复存表，供联调轮询）。

## 3.1 configs/（配置层）

- **`default.json`**——全局唯一主配置：`llm`（Ollama 地址/模型名）、`rerank`（开关，A/B 实测默认关）、`retrieval`（recall_k/top_k/双路开关）、`kb`（三库路径+切块参数）、`staff`（口令哈希）、`rate_limit`（限流阈值）、`channels`（微信）、`team`（启用的专家、rag_provider、路由温度）。**作用**：改模型/改参数不改代码。**关联**：被 `core/settings.py` 加载，`agent/router.py` 消费。
- **`logistics.json`**——运费价格表（分区/首续重/抛比系数）。**运营可直接编辑**，`business_tools.shipping_quote` 读取。
- **`production.json`**——工艺单价/工序产能表。`business_tools.order_quote / schedule_estimate` 读取。

## 3.2 core/（模型与配置的代码化）

- **`schema.py`**——全项目的数据骨架：`Role`（customer/staff）、`Intent`（9 种意图枚举）、`TicketStatus`（工单状态机）、`RequirementForm`（定制六要素+辅助字段，`missing_fields()` 返回缺失项中文标签供追问）、`Ticket`、`KnowledgeChunk`（含 `visibility` 字段——权限的载体）、`Message`。**上下游**：被所有层 import；`visibility` 决定检索层怎么过滤。
- **`settings.py`**——`Settings(BaseSettings)` 支持 .env 覆盖；`load_config()` 读 default.json；`get_settings()` lru_cache 单例。**作用**：环境变量优先于文件，生产注入口令/模型地址不落盘。

## 3.3 nlp/（轻量语言理解：规则为主）

- **`intent.py`**——`IntentClassifier`：关键词信号表（定制/尺寸/寓意/订单/投诉/员工侧/问候）→ `IntentResult`。**关键设计**：兜底**必须**返回 KNOWLEDGE 走模型（曾踩坑：兜底 SMALL_TALK 导致大量问题被硬编码话术吞掉）。**上下游**：customer/staff/team 三处入口的第一道分流。
- **`ner.py`**——`CraftNER`：5 类行业词典（针法/品类/纹样/工艺流程/材料）正则匹配。**作用**：给意图分类提供"是否行业问题"的信号；将来接图谱数据扩充词典即可。
- **`guard.py`**——提示词注入防御：9 条正则模式（忽略指令/越狱/套系统提示/套底价…），命中→国风拒绝话术+WARNING 审计日志。**关联**：customer.py 和 staff.py 入口第一步。

## 3.4 retrieval/（混合检索）

- **`bm25.py`**——手写 BM25（jieba 分词、k1/b 标准参数）。**为什么自己写**：零重型依赖、可控可测。**强项**：专有名词精确命中。
- **`vector.py`**——`EmbeddingClient`（OpenAI 兼容 /v1/embeddings，先试 OpenAI 格式再兜底 Ollama 原生 /api/embed）+ `FaissVectorStore`（IndexFlatIP + L2 归一化=余弦；save/load 持久化）。**关联**：embedding 模型名来自配置，换模型重建索引即可。
- **`reranker.py`**——CrossEncoder 精排，**离线优先**：本地 HF 缓存没有模型就直接跳过（避免联网卡死）。A/B 实测对小库负收益，默认关。
- **`pipeline.py`**——核心两件套：
  - `KnowledgeBase`：加载/切块（段落优先 300 字）/建 BM25+FAISS/**manifest 自愈**（记录每文件 mtime+size+模型名，变更自动重建）；
  - `HybridRetriever.search(query, role)`：**先按角色过滤候选集**（public/internal）→ 双路召回 → RRF → 可选精排 → top_k。**上下游**：customer/staff/team_rag 全走它或它的同类实现。

## 3.5 agent/（业务大脑）

- **`router.py`**——`AgentRuntime`：组装 embedding/llm/kb/retriever/reranker/tickets/customer/staff 的**单一入口**，`create_app` 只问它要依赖。**作用**：依赖注入根，测试时可注入假 LLM。
- **`customer.py`**——C 端核心：`CustomerSession`（消息/表单/collecting/工单引用，SQLite 持久化 WAL）+ `CustomerAgent.process`（拦截注入→拦截价格词→collecting 分支[跑题放行/退出词]→意图分流→`_stream_knowledge`[真实回答落库]→`_handle_requirement`[追问循环/表单完成建工单]）。**上下游**：web、channels 微信两路都汇到这。
- **`staff.py`**——B 端单会话版（行业答疑/复盘/文案），检索含 internal 库。
- **`ticket.py`**——`TicketStore`：SQLite 工单 CRUD（create/list/update_status/update_note）。**作用**：人工跟进的唯一凭据。
- **`leads.py`**——`LeadScorer` 纯规则意向分级：六要素齐全或出现成交信号=高。**设计点**：不耗 LLM、结果可审计。
- **`team.py`**——`TeamOrchestrator`：专家注册表 + 两级路由（`_route_by_keywords` 正则强信号零延迟 → `_route_by_llm` JSON 路由带 LRU 缓存 → 客服兜底）+ 团队会话 SQLite。**作用**：多 Agent 的调度中枢。
- **`experts.py`**——`BaseExpert`（纯知识型：RAG 检索+流式回答）/ `ToolExpert`（工具型三段式：正则提参→缺参 LLM JSON 提参[带历史]→纯函数核算→LLM 解释）+ 6 个 `ExpertSpec` 注册。**上下游**：被 team.py 派发；调 business_tools 与 team_rag。
- **`business_tools.py`**——确定性计算器：`shipping_quote`（重量+体积重抛比+分区价格表）、`order_quote`（面积×工艺单价×数量+装裱）、`schedule_estimate`（工序串并行+产能）、`ticket_stats`（只读统计）。**设计点**：LLM 禁止算术，工具只吃标量参数（`_num` 严格类型校验）。
- **`rag.py`**——**外挂知识库协议**：`Doc` 数据类 + `RAGProvider` Protocol（5 行）+ `NullRAGProvider`（空实现）+ `load_rag_provider(dotted_path)`（配置字符串动态加载实现类）。**作用**：知识来源与 Agent 解耦的契约。
- **`team_rag.py`**——协议的向量实现：扫 `team_kb_dirs` → 切块 → bge-m3 → FAISS → `retrieve()`；manifest 缓存（源变更自动重建）；`stats()` 供状态端点观测。**关联**：配置 `team.rag_provider` 指向它，换私有库=新写一个类。
- **`prompt_store.py`**——`prompts/team/*.md` 热加载（mtime 缓存，`## system` 分节）。**作用**：话术运营不改代码。
- **`prompts_team.py`**——团队内置默认提示词常量（外置文件缺失时回退）。

## 3.6 generation/（模型接入与生成）

- **`llm.py`**——`LLMClient`：OpenAI 兼容 chat/embeddings、流式 SSE 解析、**`is_ready()` 校验目标模型在模型列表里**（曾修"假在线"bug）、`missing_reason()` 诊断。**作用**：全项目唯一出网点=本机 Ollama。
- **`prompts.py`**——C/B 两套 system prompt（含"安全防线最高优先级"条款）+ 表单抽取 JSON 模板 + 三段固定话术（转人工/投诉/问候）。
- **`answer.py`**——生成装配线：`build_rag_context`（带[编号]来源的上下文）、`customer_messages`/`staff_messages`（system+历史+RAG 块+当前问）、`extract_requirement_form`（JSON mode+**只填空字段合并策略**）、`stream_grounded_answer`（三级降级：LLM 挂→抽取式引用，全挂→固定话术，每级 WARNING 日志）。

## 3.7 api/（服务层）

- **`server.py`**——所有 HTTP 端点：健康/状态/检索调试/客户 chat+history/员工 chat/工单/团队 chat+agents+status/三个确定性工具直调/渠道 webhook/指标。横切：`require_staff`（env>明文>sha256 三档+hmac 常量时间比较）、`check_rate` 限流、`_setup_log_file` 落盘日志、SSE `sse()`/`chunk_stream()`。
- **`rate_limit.py`**——`SlidingWindowLimiter`：进程内滑动窗口（线程安全 deque+Lock），按 (桶,IP) 限流，429+Retry-After。

## 3.8 channels/（多渠道接入）

- **`base.py`**——`ChannelAdapter` 抽象（verify/parse_incoming/push_reply）+ `ChannelStore`（SQLite：openid↔session 绑定、消息 ID 幂等、待推送回复队列）。
- **`hub.py`**——`ChannelHub`：注册各渠道、统一 webhook 分发、异步应答（规避微信 5 秒限制）。
- **`wechat.py`**——`WeChatAdapter`：token+sha1 验签、XML 解析、客服消息推送（access_token 缓存）。**设计点**：未配凭证=本地模式，联调零门槛。

## 3.9 web/（前端，原生无构建）

- **`index.html`**——客户页：欢迎卡片+快捷提问、聊天区、员工入口。
- **`app.js`**——SSE 逐字渲染、Enter 发送/Shift+Enter 换行、角色切换视图隔离（客户根本不渲染侧栏）、员工口令 localStorage、工单轮询、DOM textContent 渲染防 XSS。
- **`team.html`**——团队工作台（专家徽标+选择+对话）。
- **`style.css`**——国风主题（宣纸米+鎏金）。

## 3.10 data/（数据层）

- **`knowledge/`**（25 篇公开）+ **`internal/`**（2 篇内部）——主知识库：文件名=分类，段落切块，visibility 由目录决定。
- **`team_kb/`**——团队外挂挂载点（NCIFD 698 条 + 纹样民俗百科 + 经营常识 + SOURCES.md 溯源声明）。
- **`golden_test.jsonl`**——146 条黄金集，三维度标注：expected_sources（检索）/intent（意图）/behavior（行为：answer/collect/transfer/staff）。
- **`finetune/`**——四类原始数据（qa/dialogue/staff/form）+ 校验脚本规格（docs/finetune_data_spec.md）。
- **`embroidery.db`**（gitignore）——运行时唯一数据库：会话/消息/工单/团队会话/渠道绑定。

# 第四部分：面试画图与讲法模板

**画图顺序**（3 分钟白板）：
1. 先画左侧"痛点"五个框（知识/报价红线/需求散/口径乱/离线）；
2. 再画右侧架构五层，**每画一层就指回它解决的痛点**；
3. 最后圈两个"得意细节"：LLM 不算数（确定性工具）、权限在检索层不在 prompt。

**一句话收尾**：
> "这个项目让我真正理解了 Agent 工程的核心不是调模型，而是**给概率系统建立确定性边界**——数值、权限、兜底都不交给模型自由发挥，模型只做它擅长的理解与表达。"
